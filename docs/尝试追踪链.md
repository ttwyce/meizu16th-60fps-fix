### 18.6 V11/V12 之后的新认识（重要，推翻了旧假设）

1. `_sde_encoder_update_rsc_client` 共有 **3 个调用点**：`0x562A08`、`0x562A24`（都在 `_sde_encoder_resource_control_rsc_update` 0x5629C0 里）、`0x562D84`（`sde_encoder_resource_control` 的 EXIT_IDLE 分支）。
2. **该函数在开机时是必需的**：V12 把 3 个调用点全砍 → vblank 报错确实归零，但**基线直接掉到 2fps**。
   ⇒ 说明开机那一次调用是成功的（当时 vblank 可用），正是它建立了 60fps 状态。
3. **掉帧时每帧约 500ms，但这个 500ms 既不是 PP 超时（84ms），也不是 vblank 等待**：
   V12 里 vblank 失败=0，帧率仍然 2fps。⇒ **还有一个 500ms 级的等待在别处**。
4. `wait for vblank failed` 在正常 60fps 的开机阶段也会出现 22~27 次 ⇒ 它本身不足以导致 2fps。

### 18.7 结论修正

"砍掉某个等待"这条路已经证明走不通：
- 砍早了/砍多了 → 开机就 2fps（V7/V9/V12）
- 砍得准但不对路 → 没效果（V5/V6/V8/V10/V11）

**真正该找的是"那个 500ms 的等待到底在哪"**，而不是继续猜 `_sde_encoder_update_rsc_client`。
下一轮应优先做 P2（定位 500ms 来源），可用手段：
- `sde_crtc_wait_for_frame_done`（evtlog 里出现过）—— 该函数内部有 frame-done 超时
- `/sys/kernel/debug/dri/0/crtc111/` 下是否有 frame-done 计数
- 用 ftrace？`CONFIG_FUNCTION_TRACER` 未开，不行
- 用 `sde_dbg` 的 evtlog（每次超时会 dump，里面带函数名+行号+时间戳）→ **这是最靠谱的**：触摸后立刻
  `dmesg | grep sde_evtlog_dump_all` 看最后几个函数名

### 8.1 ★★ 决定性新线索：触摸会触发 light HAL 的 DC 背光扫描

清空 dmesg 后滑动 1 次，抓到触摸后 6 秒的日志：**几乎全部是**

```
[  306.430007] [0:729:light@2.0-servi] [DC_ADJ] [dsi_panel_set_backlight: 670] Backlight type:2 src_level: 13 ,dst_lvl:13
[  306.445519] ... src_level: 25 ,dst_lvl:25
... 每 ~16ms 一条，src_level 从 13 一路爬到 748 ...
```

即：**触摸 → 用户活动 → DisplayPowerController 重算亮度 → light HAL 每 16ms 调一次
`dsi_panel_set_backlight` 往死面板写 DCS 背光命令 → 每次 DCS 命令都超时（-110）→ 拖慢整条提交链。**

这才是"锁屏正常、进桌面（必须滑动解锁）就不行"的真正机制：
**锁屏时亮度策略静止（无 DCS 写入）→ 60fps；用户一交互 → 亮度扫描 → DCS 狂刷 → 2fps。**

之前 R11「杀 light HAL 无变化」是**在已经 2fps 的状态下测的**（没先恢复 60fps），结论不可靠，需要重做。

## 9. ★★★ 真正的根因定位（2026-11-09 14:22）

### 9.1 DC 背光结论作废

第 8 节把 DC 背光当"决定性线索"是错的：64 条 DC_ADJ 全挤在 1.05 秒内（一次开机亮度斜坡），
vblank 失败分布在其后 35 秒；且 `ctl.stop light HAL` 根本没停掉（卡 stopping、进程还在），N5 测试无效。

### 9.2 决定性对比（干净重启 → 触摸前/后 状态快照）

| 项 | **60fps（触摸前）** | **2fps（触摸后）** |
|---|---|---|
| `crtc111/status: vblank_enable` | **0** | **1**  ← 关键 |
| `rsc current state` | 2 | 1 |
| `client:rsc_enc25 state` | 2 | 0 |
| `solver mode status` | 0x1 | 0x2 |

已实测：触摸前 `vblank_enable:0` → `input swipe` 一次 → `vblank_enable:1` → 帧率 60→2，
且**再不自动关回去**。

### 9.3 机制

- 静止时 **vblank 中断关闭**，面板 autorefresh 自己跑（60fps，不需要 CPU 推帧/等中断）
- 一有触摸 → 框架（SurfaceFlinger / HWC）请求 vsync → **打开 vblank 中断**
- 死面板给不了 vblank → 每帧卡在等 vblank → 2fps，永久
- 这解释了之前所有"砍等待函数"补丁为何全失败：**根子是 vblank 中断被 enable 了，不是某个等待函数**

### 9.4 新的攻坚方向（纯软件优先）

1. **P6（最优先）**：找 SurfaceFlinger / hwcomposer 里"禁用硬件 vsync、改用软件 DispSync"的属性
   （`strings libsurfaceflinger.so | grep -i vsync`、`hwcomposer.sdm845.so`），
   让框架不去开 vblank 中断。`debug.sf.*` 里很可能有。
2. **P7**：内核精确改 `_sde_crtc_vblank_enable_no_lock`（用 kallsyms 定位， evtlog 里出现过此函数），
   让它永远不真正 enable 硬件 vblank（或用内部 timer 假造 60Hz vblank）。
3. **P8**：让 `vblank_enable` 打开后立刻用软件补发 vblank 事件，保持 60Hz 节拍。

**不要再碰**：pending_kickoff_cnt、wait_for_irq 全局、drm_wait_one_vblank 砍调用点、DC 背光、light HAL。

## 15. ★ 接近根因：prepare_commit 用参数 0 关闭 autorefresh（15:26 之后，纯本地分析）

### 15.1 本地反汇编结论（未刷机）

`_sde_encoder_phys_cmd_config_autorefresh`(0x569F54) 有 2 个调用点：
- `sde_encoder_phys_cmd_trigger_start+0x2c` @0x56A0BC
- `sde_encoder_phys_cmd_prepare_commit+0xa4` @0x56AF9C ← **关键**：紧前一条 `0x56AF94: movz w1,#0`，
  即**每次 prepare_commit 都用参数 0 调用 config_autorefresh**（= 关闭自刷新）。

日志里 `enc25 intf1 disabled autorefresh` 字符串 @0x1545A3D 正是这条路径打的。

### 15.2 机制（当前最合理、且能解释全部现象）

- **静止/autorefresh 开**：MDP 让面板按内部时序自刷，不需 CPU 每帧 commit、不等待 → 60fps
- **一交互** → `prepare_commit` 把 autorefresh **关掉** → 切到软件每帧 kickoff → 死面板 PP_DONE/vblank 全超时 → 2fps
- 这解释了为什么砍所有 wait/timeout/vblank-enable 调用点(K1~K14)都失败：
  **问题在"关 autorefresh"这个状态切换，不在切换之后的等待**

### 15.3 待验证方案 V15（下一个补丁，最小改动）

把 `0x56AF94` 的 `movz w1,#0`(`0x52800000`) 改成 `movz w1,#1`(`0x52800020`)，
让 `prepare_commit` **不关** autorefresh（改成 enable/保持）。
- 风险：若 autorefresh 在 prepare_commit 阶段本就该关，可能导致画面撕裂/卡死；
  但比 K1~K14 更接近"状态源"，且只改 1 个立即数、其余全不动。
- 验证点：干净重启 → 解锁进桌面 → 连续滑动 → 帧率是否保持 60。

## 18. V16 结果 + ★ 源码级完整因果链（16:30）

### 18.1 V16

| # | 改动 | 结果 |
|---|---|---|
| K14 | V16：`0x56A0B4` `ldr w1,[x1,#0x268]`→`movz w1,#1`（trigger_start 的 autorefresh frame_cnt 恒为 1，强制走自刷新分支） | **开机就 2fps**，`PANEL_DEAD=7`，`disabled autorefresh=0`。已回滚 |

强制自刷新反而更糟：`wait_for_commit_done` 里 `if (autorefresh.cfg.enable) wait_for_autorefresh_done()`
又引入一个"等 AUTOREFRESH_DONE IRQ"的等待，死面板照样不给 → 超时 + ESD 判 PANEL_DEAD。

### 18.2 ★★ 完整因果链（源码 `sde_encoder_phys_cmd.c` / `sde_encoder_phys.h`）

`KICKOFF_TIMEOUT_MS = 84`（`sde_encoder_phys.h:29`）。每次**有画面更新**的 commit 要串行等 4 个 IRQ：

```
prepare_for_kickoff  → wait_for_irq(PINGPONG,   84ms)   // 等上一帧 PP_DONE
wait_for_commit_done → wait_for_irq(CTL_START,  84ms)   // 等 CTL_START
                     → wait_for_irq(AUTOREFRESH_DONE)     // 仅自刷新开时
                     → wait_for_irq(RDPTR)                 // wait_for_vblank
```

`wait_for_irq` 超时 → `handle_ppdone_timeout()`（:469）：
- `pp_timeout_report_cnt++`，≥2 → **PANEL_DEAD + SDE_DBG_DUMP("panic")**
- `enable_state = SDE_ENC_ERR_NEEDS_HW_RESET`（下一帧还要 hw_reset）

**死面板 = 一个 IRQ 都不给** → 每帧 4 个 84ms 超时叠加 ≈ 几百 ms → **2fps**；
且超时把状态机打成 `ERR_NEEDS_HW_RESET` + PANEL_DEAD，**永久 degraded，不可逆**。

**60fps 静止（锁屏/无更新）**：根本不发生 kickoff、不进任何等待，面板按残留自刷新跑 → 60Hz。

### 18.3 这一条链解释了全部 16 个补丁为何失败

- "静止 60、交互 2"：交互=要画面更新=要 kickoff=要等 IRQ
- K1~K14 都在砍**某一个**等待/超时/使能；但等待有 4 处、且超时错误分支会把状态机打坏，砍一处不够
- V7 全局 `wait_for_irq` return 0 → 开机 2fps：破坏了必要的 IRQ 注册/同步
- V13 盲改 5 处 `#0x54` → 开机 2fps：0x54 里混了非超时常量，改坏了
- V16 强制自刷新 → 反而多一个等待 + PANEL_DEAD

### 18.4 真正对准根因的方向（V17，尚未刷）

不是"砍某个等待"，而是**让 `sde_encoder_helper_wait_for_irq` 在超时时返回 0（成功）而非 -ETIMEDOUT**——
这样每帧既不等死面板 IRQ、也不进 `handle_ppdone_timeout` 的 PANEL_DEAD/hw_reset 错误分支。
关键：必须**保留 IRQ 的 register/enable**（不能像 V7 那样整个函数直接 return 0），
只改"超时后的返回码"这一处。有了源码 + kallsyms，这次能精确定位到该函数的超时分支。

## 19. ★ 源码级根因确认：每帧 500ms = RSC vblank 等待循环（16:40）

已下载 `sde_encoder.c`（github `meizufuckers/android_kernel_meizu_sdm845@topaz`），
读通 `_sde_encoder_update_rsc_client`（就是刷了一整天 `wait for vblank failed ret:-110` 的那个函数）：

```c
#define MAX_RSC_WAIT 5
...
for (wait_count = 0; wait_count < MAX_RSC_WAIT; wait_count++) {
    if (sde_rsc_client_is_state_update_complete(sde_enc->rsc_client))
        break;                                    // ★ 想让循环立刻结束，就让它恒为 true
    if (crtc->base.id == wait_vblank_crtc_id)
        ret = sde_encoder_wait_for_event(drm_enc, MSM_ENC_VBLANK);   // ← 等死面板 vblank，超时
    else
        drm_wait_one_vblank(drm_enc->dev, pipe);                      // ← 等死面板 vblank，超时
    if (ret) {
        SDE_ERROR_ENC("wait for vblank failed ret:%d\n", ret);        // 日志里那条
        /* rsc hardware may hang without vsync. avoid rsc hang
           by generating the vsync from watchdog timer. */
        if (crtc->base.id == wait_vblank_crtc_id)
            _sde_encoder_switch_to_watchdog_vsync(drm_enc);           // 高通自带的软件 vsync 兜底
    }
}
```

### 19.1 这解释了全部现象

- **每帧 ~500ms**：`MAX_RSC_WAIT=5` × 每次 vblank 等待超时（~100ms）= 500ms → **2fps 的真凶**
- 死面板一个 vblank IRQ 都不给 → 5 次全超时 → 才 fallback 到 watchdog vsync
- 高通驱动**本来就有软件 vsync 兜底**（watchdog timer），只是每次都先硬等 5 次才用
- K1~K14 全在砍"某一个"等待/超时/使能，但**这个循环有 5 次 + 多个等待源**，砍一处不够，
  且砍到初始化就开机 2fps

### 19.2 V17 候选（源码直接支持，未刷，等指令）

| 方案 | 做法 | 依据 |
|---|---|---|
| **V17-a（最干净）** | 让 `sde_rsc_client_is_state_update_complete()` 恒返回 true → 循环第一次就 break，完全不等 vblank、不进 5 次超时 | 直接命中 500ms 循环源头，且保留 RSC 状态机其余逻辑 |
| V17-b | 把 `MAX_RSC_WAIT` 从 5 改成 1 | 减少等待次数，但仍要等 1 次 ~100ms（可能 ~10fps，不是 60） |
| V17-c | 让 `_sde_encoder_switch_to_watchdog_vsync` 无条件先生效（用软件 vsync 顶替） | 源码自带兜底，但改法比 a 复杂 |

`_sde_encoder_switch_to_watchdog_vsync` 文件偏移 0x55FADC（V4 曾误改 `hw_vsync_mode`，改的是死代码）。
`sde_rsc_client_is_state_update_complete` 偏移见 kallsyms（0x59A80C 附近，需重新核对）。

## 20. V17-a 结果：跳过 RSC 循环生效，但暴露第二条等待链（16:51，已回滚）

| # | 改动 | 结果 |
|---|---|---|
| K15 | V17-a：`sde_rsc_client_is_state_update_complete`@0x59A80C 改成 `mov w0,#1; ret`（恒 true） | **`wait for vblank failed`=0（补丁生效，5 次循环确实跳过），但开机就 2fps**；`kickoff timed out=8`、`PANEL_DEAD=7`。已回滚 |

### 20.1 决定性认识：每帧有【两条独立】等待链

源码显示掉帧不是单一循环，而是两套各自等死面板 IRQ 的机制：
1. `sde_encoder.c` 的 `_sde_encoder_update_rsc_client`（RSC vblank 循环，5×100ms）← V17 已跳过
2. `sde_encoder_phys_cmd.c` 的 `prepare_for_kickoff`→`wait_for_idle`（PINGPONG, 84ms）、
   `wait_for_commit_done`→`wait_for_ctl_start`（84ms）、`wait_for_vblank`（RDPTR, 84ms）
   → 超时进 `handle_ppdone_timeout` → PANEL_DEAD + hw_reset  ← **V17 没碰到，仍在超时**

砍掉第 1 条，第 2 条照样每帧 84ms×N 超时 → 2fps。这解释了 K1~K17 全失败：
**一直在各调用点分别砍，而两条链都汇到同一个底层函数**。

### 20.2 真正的总闸：`sde_encoder_helper_wait_for_irq` / `wait_event_timeout`

`phys_cmd.c` 里所有等待最终都调 `sde_encoder_helper_wait_for_irq(phys, INTR_IDX_*, &wait_info)`，
其内 `wait_event_timeout(wq, atomic_cnt==0, msecs_to_jiffies(wait_info->timeout_ms))`，
超时返回后 `report_irq_timeout` → `handle_ppdone_timeout` → PANEL_DEAD/hw_reset。
- V7 全局把 `wait_for_irq` 第一条指令改成 `ret` → 开机 2fps：**破坏了 IRQ 的 register/enable**（该函数不止等待）
- 有了源码，正确改法应在 `wait_event_timeout` 内部：**让超时路径返回 0（视为成功）而非负错误码**，
  这样每帧不进 PANEL_DEAD/hw_reset 错误分支，fence 立即释放、SF 不阻塞

### 20.3 下一步（V18 候选，需读 `sde_encoder_helper.c` 源码核准，未刷、等指令）

读 `drivers/gpu/drm/msm/sde/sde_encoder_helper.c` 里 `wait_event_timeout` / `wait_for_irq` /
`report_irq_timeout` 的实现，找到"超时→负返回"那一处，改成返回 0。
这是所有等待的唯一汇聚点，比在各调用点分别砍更接近"一次改对"。

### 20.4 诚实的话

17 次补丁全失败。每次"补丁生效但无效"都在证明：这不是一个点，是**多条等待链 + 超时错误分支
把状态机打进 PANEL_DEAD**。V18 若还不成，字节补丁这条路就该认输了——
剩下只有"从完整源码改驱动、编译内核"一条路（用户已允许换 ROM/有源码）。

### 21.2 ★ 决定性发现：MoKee 这个 ROM 用的是「预编译内核」，没有从源码编译内核的流程

即 MoKee 官方打包的是**魅族原厂 prebuilt 内核**（就是本机这个 4.9.65 Flyme 内核），

### 21.3 结论：不能「直接适配/整包替换」，风险高

1. **vendor 强绑定**：sdm845 闭源 HAL（显示/相机/指纹/触控/音频/WiFi）依赖特定内核驱动接口、

2. **本机全靠 adb/scrcpy 操作**（屏幕坏）。万一新内核把 USB gadget / 触控搞挂，
   **没有救机手段**，比刷 boot 补丁危险得多。
3. 需要 dtbo / vendor / ramdisk / AVB 全匹配，编译产物不能直接 dd 进现有 boot。
4. 环境门槛：Linux + AOSP 特定版 clang + 1GB+ 源码（本会话 raw 下载已多次超时）。

### 21.4 但源码的价值已经兑现，且不需要整包编译

- 语言层面：**4.9.65 与 4.9.227 的 sde 显示驱动代码基本一致**（十几个补丁的符号偏移全部对应得上）。
  所以「用源码读懂逻辑 → 回到本机 4.9.65 Image 上打精确补丁」完全成立。
- 方案 A 真正不可替代的优势不是「换内核」，而是「**一次能改多处 + 能加日志/重编译验证**」——
  这是单选点字节补丁做不到的（V17 已证明：砍一处不够，要同时改 PANEL_DEAD 判定 + vsync 兜底 + 多处超时）。
- 更稳妥的落地：**不改 ROM，只在本机 boot.img 的 kernel 段一次性打「源码确认的多点补丁」**，
  保留原 ramdisk/dtb/AVB/vermagic。相当于「A 的精准度 + 零兼容风险」。

### 21.5 待用户决定

- 路线①（推荐）：源码指导 → 本机 Image 多点精确补丁组合（如同时改
  `handle_ppdone_timeout` 不置 PANEL_DEAD + `wait_event_timeout` 超时返回 0 + 维持 watchdog vsync），

## 23. 路线① 结论：V18/V19 是净退步，已回滚（17:24）

### 23.1 关键实测（同一把尺子：scrcpy --print-fps，静止不触摸）

### 23.2 为什么是退步

V18 的两点（超时返回 0 + 84ms→1ms）虽然清掉了全部 SDE 错误（这是真发现），
但**同时破坏了"静止时走自刷新、不等 IRQ"的 60fps 状态**——缩短超时/跳过错误路径后，
编码器不再维持那个"不等待"的快路径，于是静止也掉到 10fps。

**教训：不能全局改超时/等待**（与 V7/V13 的教训一致，但这次更明确：
不是"开机挂"，而是"把 60fps 快路径一起改没了"）。

### 23.3 本轮真正的、可复用的收获

1. **确认 2fps 交互卡顿来自 SDE 错误路径**：`wait_for_irq` 超时 → `handle_ppdone_timeout`
   → `PANEL_DEAD` + `SDE_ENC_ERR_NEEDS_HW_RESET` → 状态机永久 degraded。
   把这条错误路径断掉，交互帧率确实从 2 → 10fps，且 dmesg 零 SDE 错误。
2. **确认 10fps 不是 SDE 等待造成的**：V19 把等待变成零耗时，仍 10fps。
   瓶颈在 fence 释放节奏 / SF 合成节拍，不在 SDE 内部等待。
3. **确认"静止 60fps"依赖的是自刷新快路径**，任何全局改超时都会把它弄坏。

### 23.4 V20 候选（更外科手术式，避免伤到 60fps 快路径）

**只切断"永久降级"，不动任何超时长度、不动等待本身：**

- 目标：`_sde_encoder_phys_cmd_handle_ppdone_timeout`(源码 :469) 里
  ①不置 `SDE_ENCODER_FRAME_EVENT_PANEL_DEAD`
  ②不设 `phys_enc->enable_state = SDE_ENC_ERR_NEEDS_HW_RESET`
  但**保留**它原有的 fence 释放逻辑（`handle_frame_done` 信号 retire fence）——否则会冻结。
- 这样：静止仍走自刷新 60fps；交互时即使 PP 超时，状态机也不被打死，
  下一帧还能恢复正常（而不是永久 2fps）。
- 需要先精确定位该函数里 `pp_timeout_report_cnt >= PP_TIMEOUT_MAX_TRIALS(2)` 分支
  和 `enable_state = 3` 的写入点（本地反汇编 + kallsyms，纯只读）。

## 25. 路线A（SF backpressure）实测失败 + 根因再确认（17:55）

### 25.1 源码级唯一真因（本轮想清楚的结论）

`sde_encoder_phys_cmd_ppdone_irq()`（面板发完一帧后触发的中断）里只做两件事：
```c
event = SDE_ENCODER_FRAME_EVENT_DONE | SIGNAL_RELEASE_FENCE;
handle_frame_done(parent, phys_enc, event);              // ① 释放 release fence → SF 才能渲染下一帧
new_cnt = atomic_add_unless(&pending_kickoff_cnt,-1,0);
wake_up_all(&pending_kickoff_wq);                        // ② 唤醒 wait_for_idle（84ms 等待等的是它）
```
**面板坏了 → PP_DONE 永不触发 → ①②都没人做。** 22 个补丁全在处理"①②没发生之后"的后果
（等多久、错误态怎么打、vblank 怎么兜底），**没有一个去补 ①② 本身**。

- 移除脚本、重启复核：V20 静止 **60fps** 确认恢复
- ⇒ **该属性确实生效了，但对本场景是负优化**（SF 不等 fence 后节拍反而乱）

### 25.4 剩下唯一根治路线（V23）：合成 PP_DONE

1. 调 `sde_encoder_frame_done_callback`(0x564BF0) 且 event 含 `SIGNAL_RELEASE_FENCE` → fence 立即释放
2. 递减 `pending_kickoff_cnt`(phys_enc+0x290 附近) + `wake_up_all(&pending_kickoff_wq)` → 等待立即返回

- 效果：fence 立即释放、零超时、不进错误路径；且 `trigger_start` 只在真正更新帧时调用，

- 难点：`ppdone_irq` 被内联（kallsyms 无该符号），需在函数尾部找代码洞塞 ~8-10 条指令，
  且要正确构造 x0=parent、x1=phys_enc、w2=event 三个参数

## 28. 金丝雀测试：抓到致命 bug，但恢复通道实战验证成功（18:27）

### 28.1 金丝雀镜像

`boot_canary.img` = V20 两点 + 代码洞绕道
- 代码洞：`_sde_encoder_phys_vid_wait_for_vblank` @ `0x566864`（命令模式下永不调用，648 字节空间）
- 调用点：`0x56A0E8`（trigger_start 里 `bl helper_trigger_start`）→ 改跳代码洞
- 洞内：`bl 0x55FE98` + `ret`
- md5 `e55729544d1de31162df633355884acb`

### 28.2 结果：**开机卡死（hang），adb 全无**

### 28.3 ★ 我的 bug（金丝雀的价值就在这里）

```
0x56A0E8  bl CAVE      → LR = 0x56A0EC，跳洞
CAVE+0    bl REAL      → LR 被改成 0x566868（洞内地址），跳 REAL
REAL...   ret          → 回到 0x566868（洞内）
CAVE+4    ret          → 又跳回 LR = 0x566868  ← 死循环！
```
**内层 `bl` 覆盖了 LR，导致第二个 `ret` 自循环。**

### 28.4 正确写法（下次用这个）

```
0x56A0E8  bl CAVE      → LR = 0x56A0EC
CAVE+0    b  REAL      → LR 不变，纯尾跳
REAL...   ret          → 直接回到 0x56A0EC ✓ trigger_start 收尾正常执行
```
**用 `b` 而不是 `bl`，LR 不被污染。** 若洞内需多条指令，则必须 `stp x29,x30,[sp,#-N]!` 保存 LR、
用完 `ldp x29,x30,[sp],#N` 恢复后再 `ret`。

## 30. ★★★ 突破：V27 实现桌面 60fps！（但 25 秒后 panic）

### 30.1 关键发现：SF 等的是 RETIRE fence，不是 RELEASE fence

V24/V26 只发 `SIGNAL_RELEASE_FENCE(0x8)` → 桌面 10fps（内核零错误、精确 100ms 周期）。
V27 改为 **`0x9 = RETIRE(1) | RELEASE(8)`** → **桌面滑动稳定 57~67fps ≈ 60fps！**

`ppdone_irq` 里真正被 SF 用作 present fence 的是 **retire fence**，release fence 只给 app 用。
这一条是整场最关键的认知。

### 30.2 各版本结果

| 版本 | 事件 | 递减计数 | 静止 | 桌面滑动 | 稳定性 |
|---|---|---|---|---|---|
| V24 | 0x8 | 无 | 58~60 | 10~12 | 稳定 |
| V26 | 0x8 | kickoff | 10 | 10 | 稳定（零超时零错误） |

### 31.2 V29 结果：0fps 全冻结

**偏移是对的，但帧率 0fps。**

### 31.3 原因：时机错了

`pending_retire_fence_cnt` 由 virt 层在**一帧被排队时**递增、在 **fence 真正 signal 时**递减。
在 `trigger_start`（帧刚开始发）就递减，等于**提前消耗了还没到期的计数** →
后续真实 retire fence 得不到正确 signal → SF 永远等 present fence → **0fps**。

对比：
- **V27**（0x9 但**不递减**）：60fps 但计数只增不减 → 同一 fence 被反复 signal → 约 25s 后 panic
- **V29**（0x9 且递减）：计数被提前吃掉 → 0fps
- ⇒ 正确做法必须在**正确的时机**配对（signal 与 decrement 同时、且在该 fence 到期之后）

### 31.4 剩余正确解法（需要更精细的挂点）

1. **挂 `handle_post_kickoff`**（帧已发出后）而不是 `trigger_start`
2. 或直接**重写 `ppdone_irq` 为一个可调用函数**：它在 0x56A… 区间被内联了，
   但 `sde_encoder_frame_done_callback` 之外的逻辑（retire/kickoff 计数）必须按原顺序执行
3. 最稳妥：**编译内核源码**，在 `ppdone_irq` 里加一个定时器/软中断定期模拟调用，
   让计数与 signal 天然配对 —— 而不是在错误时机手工插桩

## 34. V32~V34：fence 合成的最后三个变体（2026-11-10）

### 34.1 关键发现：V29 的 0fps 不是时机问题，是我机器码写错

从源码确认递增顺序（`sde_encoder.c` `_sde_encoder_trigger_flush` 第 3386~3394 行）：

```c
pending_kickoff_cnt = sde_encoder_phys_inc_pending(phys);   // 递增 kickoff
if (is_master) atomic_inc(&phys->pending_retire_fence_cnt);  // 第3389行，递增 retire
phys->ops.trigger_flush(phys);
```
`trigger_start` 在其后调用 → **V29 在 trigger_start 递减的时机是对的**。

真正的问题：我的 `stlxr` 用了 `0x88007C00` 作基址，正确应为 `0x8800FC00`(STXR) / `0x8808FC00`(STLXR)。
写错的 `0x88077CA6` 是**非法编码 → undefined instruction → oops → 显示死但系统活**（正是 0fps 现象）。

### 34.2 三个修正后的变体实测

| 版本 | 事件 | 递减 | md5 | 结果 |
|---|---|---|---|---|
| **V32** | `0x9` RETIRE+RELEASE | retire + kickoff | `85a14a7e…` | **0fps**（系统活，up=118） |
| **V33** | `0x9` | 只减 retire | `a02bc0bf…` | **0fps** |
| **V34** | `0x1` RETIRE only | 无 | `451f130e…` | **0fps** |

### 34.3 完整规律（关键结论）

| 版本 | 事件 | 递减 | 结果 |
|---|---|---|---|
| V24 | `0x8` RELEASE | 无 | 10fps |
| **V27** | **`0x9` RETIRE+RELEASE** | **无** | **57~67fps，25s 后 panic** |
| V33 | `0x9` | 减 retire | 0fps |
| V34 | `0x1` RETIRE | 无 | 0fps |
| V32 | `0x9` | 减 retire+kickoff | 0fps |

**⇒ 只有 V27（发 RETIRE+RELEASE、不递减）能到 60fps；任何递减改动都直接冻结；只发 retire 也冻结。**

推断：SF 需要 **release 和 retire 两个 fence 都被释放**，且 `pending_retire_fence_cnt` 必须保持 >0
（超时兜底路径 `handle_ppdone_timeout` 会读它并再次 signal retire，可能是 60fps 的真正来源；
一旦我们把它减到 0，兜底路径就跳过了 → SF 饿死 → 0fps）。而 V27 之所以 panic，
正是因为兜底路径**重复 signal 同一个 retire fence** → fence 对象损坏。

**这是一个自相矛盾的结构：不减 → 60fps 但重复 signal 导致 panic；减 → 不 panic 但 0fps。**

### 34.4 结论

字节补丁这条路在 retire fence 计数上陷入死结，无法在"不 panic"和"不冻结"之间同时满足。
要突破必须能**改源码重编译**（在 pp_tx_done_irq 里正规实现），而公开源码树编出的内核
因缺魅族专有早期初始化而无法启动（见 §33）。

**根因：显示缓冲区 use-after-free。**

但硬件实际只按 ~10fps 消费（因为 `pending_kickoff_cnt` 从不递减，

```
bl sde_encoder_frame_done_callback
add x5,x19,#0x290                          ; &pending_kickoff_cnt

```

**不动 `pending_retire_fence_cnt`（0x294）** —— 这是与失败的 V32 的关键区别。

## 37. ★ V39：修复 ctl_start 偶发超时（2026-11-10）

### 37.1 现象

V38 之后用户反馈"还是会卡"。排查发现新的**偶发**错误：

## 38. ✗ V39 失败：递减 ctlstart 导致 GPU 死锁（2026-11-10）

### 38.1 现象

V39 刷入后约 8 分钟，用户报告"是不是卡死了"。实测：

```
vsync 增量 = 0            ← 显示管线停摆
service input: not found  ← system_server 的 input 服务挂掉
SF 卡在 adreno_drawctxt_wait → kgsl_ioctl_device_waittimestamp_ctxtid
watchdog 触发 backtrace
```

**SF 死等 GPU 时间戳，GPU 永远不完成 → 显示冻结。**

### 38.2 根因：ctlstart 不能像 kickoff 那样提前递减

V39 在 `trigger_start` 后立即递减 `pending_ctlstart_cnt`，让
`wait_for_ctl_start` 立即返回、驱动认为"帧已开始"。但硬件 CTL_START 实际没发生
（面板坏了中断不来）→ 显示管线时序错乱 → 后续 rd_ptr / 提交完成链断裂 →
GPU fence 永远等不到 → SF 死锁。

**关键区别**：
- `kickoff` 递减安全（V36/V38 证明）：`wait_for_idle` 等的是"提交完成"，我们已用 frame_done 信号替代。
- `ctlstart` 递减危险：`wait_for_ctl_start` 等的是"帧真正开始扫描"，这是硬件时序的起点，
  不能伪造。

### 38.3 处理

- 立即回滚 **V38**（`f631bfa8…`），设备恢复，input 服务正常。
- 丢弃 V39（`0c90bc5f…`），镜像保留在 00_最终成果 作证据。

### 38.4 遗留问题：V38 的偶发 ctl_start 超时仍待解决

V38 偶发 `ctl start interrupt wait failed`（84ms 掉帧），是用户最初感觉"卡"的来源。
正确解法不是伪造 ctlstart，而是：
- 方向 A：扩大 `ctlstart_timeout` / 改 `get_start_state` 判断，让超时后不报错
- 方向 B：查 `sde_encoder_helper_wait_for_irq` 对 INTR_IDX_CTL_START 的超时后处理，看能否在 frame_pending 时也 ret=0
- 方向 C：接受 V38（偶发掉帧，但整体 43~61fps 可用）

## 39. ★★★★★ V40 最终版：修复"停止再滑动"卡顿（2026-11-10）

## 40. ★★★★★ V42 最终定版：修复恢复卡顿 + 0fps 溢出（2026-11-10）

### 40.1 V40/V41 的教训

- **V40**（驱动层 no-op unregister RDPTR）：DRM 层仍置 `vblank_enable=false` → 状态不一致 → 黑屏 0fps。
- **V41**（DRM 层 vblank 永不关闭）：恢复流畅，但 SF 持续提交 → 每帧等 CTL_START 中断
  → 面板坏中断不来 → 84ms 超时 → commit 失败 → retire 槽堆积 → `retire event overflow` → 0fps。

### 40.2 根因链（dmesg 证据）

```
ctl start interrupt wait failed
wait for commit done returned -110
crtc111 retire event overflow   ← 固定大小 retire_events[] 槽耗尽
```

### 40.3 修复：V42 = V41 + ctl_start 超时后 ret=0

`wait_for_ctl_start` 超时后，驱动**本来就有**降级处理（signal retire fence + 递减
ctlstart + 递增 ctlstart_timeout），但 `ret` 仍返回 -ETIMEDOUT 给上层 → commit 失败。

```
0x56ae64: 12800db4 (movn w20,#0x6d = -110)  →  52800014 (movz w20,#0)
```

超时后 ret=0 → commit 不再失败 → retire 槽正常释放 → 不溢出。

**与 V39 的本质区别**：V39 在 0ms 伪造"帧已开始"（硬件未动 → use-after-free → GPU 死锁）；
V42 是等满 84ms 后放弃等待（硬件有足够时间，安全）。

## 42. ★★★★★ V53 定版：守卫式代码洞 + 撤回谎报补丁（2026-11-10 晚）

## 43. 附：esdfix.sh 的 remount 搞挂 WebView（2026-11-10 晚）

### 43.1 症状
